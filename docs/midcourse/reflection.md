# Reflection — Mid-Course Project

For this mid-course project I used Claude (in a step-by-step guided mode) as my primary AI pair-programmer for planning, code changes, and documentation. This built on GitHub Copilot in VS Code, which I had used throughout Modules 1-3 for both the Python/FastAPI backend and the JavaScript frontend code.

Working through this project reinforced how valuable a slow, step-by-step AI-assisted workflow is when you're not a programmer yourself. Rather than asking the assistant to generate a whole feature in one shot, I had it walk me through one small change at a time — one field, one function, one test — and I verified each step before moving to the next. This made the process manageable under a tight deadline, and when something did break, I could narrow down where the problem was instead of debugging a wall of unfamiliar code.

One moment AI clearly helped was in choosing the two features. Given five options and a hard deadline, I asked it to recommend the two simplest given the time constraint, and it correctly identified that tags/labels and due dates/overdue only required adding fields to existing models, not new entities or state machines — saving me from picking something too ambitious to finish.

One moment AI slowed things down was during test writing: when I manually copy-pasted a generated test function, part of its JSON body was accidentally lost in the paste, which caused a syntax error and made an unrelated test silently absorb the broken function's body. This wasn't something AI got wrong in its output — but the back-and-forth of me describing the error, AI asking to see the file, and going through several rounds before we found the real cause took longer than expected, since I was still learning to read the Python code well enough to spot the missing lines myself.

A moment where my own review changed the result was the overdue-status design. AI's first suggestion was to store `is_overdue` as a persisted field on each task, updated by a background job. I pushed back on this as overkill for the project's scope and asked for it to be computed live instead, on every read and write. This was a better fit for an in-memory, no-database project, and it removed an entire category of "stale flag" bugs before they could happen.

Testing manually through Swagger UI before writing automated tests was also valuable — seeing the actual JSON response with `is_overdue: true` gave me confidence the logic was right before I asked for pytest tests to lock it in. The Break Tests at the end (deliberately breaking the tag filter and overdue logic, confirming the relevant test failed, then restoring it) were the final piece of evidence that the new tests do real work rather than passing trivially.

If I did this again with more time, I'd add a UI element for filtering by tag or overdue status directly, since the backend already supports it via query params but the frontend doesn't expose it yet.
